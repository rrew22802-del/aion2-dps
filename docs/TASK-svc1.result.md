# Отчёт svc1 / 2.6.0

## A. Поиск игрового захвата

- Npcap открывает все пригодные интерфейсы до начала общей трёхсекундной проверки; устройства проверяются параллельно. Потоки учитываются только по пакетам, начинающимся с `0E 00 36`, не по совпадению внутри TLS/другой полезной нагрузки; для одного потока по-прежнему нужно минимум 3 попадания.
- Приоритет выбора: loopback, затем виртуальный туннель/адаптер, затем физический интерфейс. Добавлены названия Happ, xray, sing-box, v2ray, Clash, Wintun, WireGuard, TAP/OpenVPN, Outline, ExitLag, GearUP, NoPing, LagoFast, Mudfish, Radmin, ZeroTier и Hamachi. Безадресные интерфейсы пропускаются, кроме loopback и распознанных туннелей; отключённые пропускаются по флагу Npcap, если он предоставлен.
- При отсутствии цели цикл занимает примерно 4 секунды (3 секунды захвата + 1 секунда ожидания). После выбора отслеживается активность точного набора портов; 8 секунд тишины останавливают захват и запускают поиск заново. Лог содержит инвентарь, приоритет, число magic-пакетов по каждому интерфейсу/потоку и причину выбора.
- Добавлены синтетические unit-тесты raw IPv4, Ethernet, DLT_NULL, HTTPS-шум, пропуска безадресного WAN Miniport и выбора Happ при одинаковом потоке на виртуальном и физическом интерфейсах.

## B. Timeline

- Добавлен `GET /v1/fights/{fightId}/timeline?player={id}` для `current` и архивного боя. Ответ содержит урон игрока/группы по секундам, casts игрока и интервалы баффов, применённые к игроку и сохранённые существующим парсером.
- Ограничение ответа: 1 200 секундных корзин и 25 000 casts. История сохраняет до 25 000 событий на бой и только первые 20 минут от начала; документация API обновлена.

## C. Healing / HPS

- Healing-коды больше не просто отбрасываются: если `ParsedDamagePacket` содержит ненулевое количество, оно суммируется по персонажу и целям. Для боя healing сопоставляется текущей цели группы; HPS делит сумму на длительность боя. Игрок, который только лечит, добавляется в список игроков последней цели.
- Парсер создаёт `ParsedDamagePacket` только при наличии разобранного значения урона/лечения; пакет без такого значения не увеличивает сумму. Проверить отдельный вариант протокола без суммы по записи нельзя.

## D. Combat power / смерти

- Существующая таблица dispatch направляет `45 36` в парсер данных группы, который извлекает CP по маркеру `F4 CB 1F`; `56 36` несёт CP основного персонажа в `u32` по смещению 2. CP уже хранился в storage, теперь отдан в `players[].cp` и архивные сводки.
- Отдельного death opcode в таблице нет: событие смерти — `00 8D`, HP игрока равен нулю после varint ID и трёх промежуточных varint. Ранее фиксация была закрыта режимом PvP; теперь смерти учитываются независимо от него и отдаются как `players[].deaths`.
- `docs/PACKETS-cp-deaths.md` описывает opcode, поля и примеры из `.captures/auto-1791320045289.aetherpc` и `.captures/live-2026-10-06-happ.pcapng`. В raw-IP pcapng разобрано 23 651 кадр игрового TCP-порта 13328; поиск байтовых сигнатур подтверждает CP/member-info и zero-HP шаблон. Счётчики сегментных сигнатур не выдаются за число игровых сообщений.

## Версия и проверка

- Версия выставлена в `2.6.0` в Cargo manifest/lock, Tauri config и `package.json`; добавлена запись в `CHANGELOG.md`.
- `cargo test` и `cargo build` не запускались: `cargo` не установлен в доступной среде. `git diff --check` выполнен без ошибок форматирования whitespace.
- `pingMs` оставлен на существующем PingTracker. Он получает нормализованный TCP payload после снятия link-layer заголовка, поэтому raw-IP и loopback не требуют отдельных веток. В последней `.aetherpc` найдено 12 маркеров `03 36 00 00`, но ни один не дал допустимую RTT по алгоритму PingTracker; `null` согласуется с отсутствием валидной временной метки, хотя этот захват не подтверждает ситуацию на owner PC после обновления.
- Открытое ограничение: CP извлекается текущей эвристикой маркера и правдоподобного числа; конкретная граница поля не подтверждена изолированным полным server message. Устройство формата смерти подтверждается `00 8D` zero-HP примерами, но отдельный death opcode не найден.
